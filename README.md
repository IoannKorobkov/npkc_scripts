## ✅ Как устроен мультискрипт

`all_dashboards_up.py` — одна задача планировщика, которая внутри запускает 22 отдельные подзадачи (каждая — свой `.py`-файл, отвечает за одну таблицу/витрину/дашборд). Работает так:

1. **Старт:** создаётся lock-файл (сигнал для сторонних проверок, что скрипт работает) и файл с полным логом прогона.
2. **VPN включается один раз** для всех 22 подзадач сразу.
3. **Фаза извлечения:** по очереди достаёт данные из source ClickHouse во временные буферы для каждой из 22 подзадач.
4. **VPN выключается** — уже не нужен для загрузки в целевые БД.
5. **Фаза загрузки:** по очереди грузит данные из буферов в целевые БД (target CH или PostgreSQL).
6. Если какая-то подзадача упала — это не останавливает остальные 21, ошибка просто фиксируется в логе.
7. **Итог:** отчёт «успешно / с ошибкой» уходит в ntfy (push) и в два чата Битрикс24 (подробный лог + короткая сводка со ссылками на дашборды).
8. Lock-файл удаляется, код завершения: 0 (всё ок), 1 (частичные ошибки), 2 (упало ≥70%).

Отдельно: `guide_dismissed_up.py` (№22) не требует VPN вообще (работает через Bitrix24 API напрямую), поэтому выполняется сам по себе, вне общих фаз.

## 🔁 Если мультискрипт не отработал

Прогнать все скрипты вручную по одному, сначала в порядке приоритета, при каждом перезапуске сверить `DAYS_TO_SYNC` с конфигом мультискрипта.

**Порядок при ручном запуске:**

1. `instrumental_3w_up.py`
2. `concl_click_up.py`
3. `стади_up.py`
4. `svo_eris_llo_up.py`
5. `vitrina_sync.py`

Остальные — в любом порядке. После прогона — проверить свежесть данных на дашбордах. Если стади/конклы несвежие — заявка на SD; если другие витрины не обновляются 2+ дня — тоже заявка.
